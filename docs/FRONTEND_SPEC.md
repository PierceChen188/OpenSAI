# OpenSAI 前端功能规格说明书

> 面向**前端设计师 / 前端工程师**。本文**只规定前端要实现哪些功能**，以及每个功能背后**依赖后端的哪些数据**（保证可落地）。
> 本文**不涉及任何视觉风格**（不谈配色、字体、UI 风格、动效观感）。文中提到"高亮""流动""区分"等，均指**为了传达信息而必须具备的功能性可视编码**，不是美术建议——具体怎么好看由设计阶段决定。
> **界面语言：全部英文（English UI）。** 本文用中文书写，但前端所有用户可见文案一律英文。

---

## 0. 这个产品是什么（一句话）

OpenSAI 是一个 **DAG 计算卸载平台**：用户把一个任务拆成有依赖关系的子任务（一张 DAG），平台**智能决定每个子任务放到哪台设备**、**给它分配多少资源**，并在设备间通过**数据面**自动传输中间产物，最后按依赖汇总结果。

前端要做的事，归结为**展示并操作这套系统的六大能力**（本文的主线）：

1. **动态编辑设备拓扑**
2. **智能放置（把子任务放到哪台设备）的决策过程**
3. **适配优化（给每个子任务分多少资源）的决策过程**
4. **多维资源控制（CPU 核 / 内存 / 出口带宽 / 存储）**
5. **多链路传输（中继多链路、多网卡聚合及其叠加）**
6. **一个三维动态拓扑窗，用流动方式直观呈现以上全部过程**

> 设计目标：打开前端，**不用读文档就能看懂"任务是怎么被聪明地放下去、资源怎么分、数据怎么在设备间多路并行流动的"**——这就是产品的核心卖点。

## 1. 名词速查（先建立共同语言）

| 名词 | 含义（前端要展示的对象） |
|---|---|
| **DAG / 子任务(节点) / 依赖** | 一个任务图；节点之间有先后依赖（前驱 → 后继）。 |
| **设备(device)** | 一台执行子任务的机器（边缘节点）。有算力(核)、内存、磁盘、网卡、并行槽位等属性。 |
| **链路(link)** | 两台设备之间的网络通道，有实测带宽与时延。 |
| **放置(placement)** | 决定"某子任务跑在哪台设备"。三种模式：`plan`（整图前瞻就近，默认）、`smart`（逐节点贪心）、`random`（对照基线）。 |
| **资源档位(allocation)** | 给某子任务分配的 CPU 核 / 内存预算 / 传输带宽 / 存储配额。可显式声明或由系统自动决定。 |
| **大脑账本(ledger)** | 系统为防止"超卖"维护的预留记录：放置预留、已承诺带宽、已承诺存储、在飞任务。只在中枢内存里。 |
| **数据面 / 跨设备传输** | 上游产物经 QUIC 在设备间直传给下游；若上下游在同一台机器则**本地直读**（省传输）。 |
| **多链路传输** | 一次传输同时走多条物理路径并行（经中继 / 多块网卡），带宽叠加。 |
| **makespan** | 整张 DAG 的端到端完成时间，越低越好。 |
| **算法历史画像** | 每个算法的实测资源/耗时统计（用于自动定档与预测）。 |

## 2. 信息架构总览

前端以**一个三维拓扑窗为主视图（主舞台）**，其余功能以侧栏 / 抽屉 / 浮层 / 子页围绕它组织。建议模块：

| 模块 | 角色 | 对应优势点 |
|---|---|---|
| **① 三维拓扑动态窗** | 主舞台：实时呈现集群、放置、传输、资源全过程 | ⑥（统领 ①②③④⑤） |
| **② 拓扑编辑器** | 增删设备/连边/设属性、手动钉选、情景(what-if) | ① |
| **③ 放置决策面板** | 逐子任务展示候选→筛选→打分→选中 | ② |
| **④ 资源决策面板** | 逐子任务展示四维档位如何定 + 账本变化 | ③④ |
| **⑤ 传输面板** | 每次传输的路径构成（直连/中继/多网卡/聚合） | ⑤ |
| **⑥ 任务编排** | 画 DAG、设参数、提交 | 操作入口 |
| **⑦ 运行结果与对比** | makespan、放置结果、跨设备传输、plan vs random | 价值证明 |
| **⑧ 集群监控** | 资源指标卡 + 设备卡 + 链路 + 画像 | 基础态势 |
| **⑨ 系统参数 / 算法库** | 在线调参、算法目录与上传 | 配置 |
| **⑩ 全局：连接状态 + 时间轴 + 模式切换(Live/Replay/Edit/Compare)** | 贯穿 | — |

> 模块可合并/重排。**①三维窗是默认落地页与对外演示的亮点**，②~⑤本质上是①里某个对象被点选后展开的"详情/过程"，既可做成①的联动浮层，也可做成独立页。
>
> **关键原则（务必遵守，避免本末倒置）：三维窗是"锦上添花"，不是唯一入口。** 下面 §2.5 列出的**基础功能底座**优先级最高、必须独立成立——**所有数据与操作都必须有常规的列表 / 表格 / 表单视图**，使产品在**完全不打开三维窗的情况下也能正常提交任务、看监控、看结果、管算法**。三维窗负责"直观与演示"，基础视图负责"可用与日常"。先保证后者，再谈前者。

## 2.5 基础功能底座（最高优先级 · 必须先成立）

这一节是产品的"地基"：即使去掉所有炫技可视化，下面每项也必须完整可用、稳定可靠。**验收标准：第一次用的人不依赖三维窗，也能独立完成"连上集群 → 提交任务 → 看结果 → 管算法/参数"的完整闭环。**

本节只列**"必须具备什么"**；**"具体怎么做"统一放在所指的详节里，不在此重复**（避免与 §9–§12 内容打架）：

| 底座能力 | 必须具备（要点） | 详节 |
|---|---|---|
| **全局框架** | 模块导航；全局连接状态（已连 / 无设备 / 断连 + 自动重连提示）；默认落地页可配；每页四态（加载 / 空 / 错误 / 正常），绝不白屏或无限转圈 | §2、§15 |
| **任务生命周期** | 创建/编辑 DAG、提交（明确成功/失败反馈）、**任务列表**（状态：排队/运行/完成/失败/超时，可排序筛选）、任务详情、重跑/改参重提、实时状态跟踪 | §9（编排）、§10（列表/详情/历史/重跑） |
| **结果查看** | 常规表格视图：makespan、节点明细（设备/耗时/产出/结果，出错标红）、逐节点返回值/错误、历史结果 | §10 |
| **集群/设备常规视图** | 设备列表/表格（在线、四维资源 已用/已承诺/可用/总、并行槽位、任务数、RTT）、链路列表（带宽/时延，可空）、~2s 实时增量刷新 | §11 |
| **算法管理** | 算法目录（说明/参数/是否产出·需前驱）、上传 `.py`（校验 + 反馈）、实时拉取已注册算法 | §12.2 |
| **系统参数/连接** | 查看·修改安全可调项（回显生效值）、只读项标注"需重启"、后端连接地址可配 | §12.1 |
| **基本可用性** | 关键操作明确反馈、表单校验防呆（DAG 不成环/必填/范围/只暴露安全参数）、列表搜索筛选排序、友好错误提示与指引 | §9、§15 |

> **优先级声明**：§2.5 底座 = **P0（必须做、必须稳）**；§3–§8 的六大优势可视化 = 叠在底座之上的**差异化亮点**。**底座不达标之前，炫技没有意义。** 且每个优势可视化（②③⑤⑥）都应有**常规视图兜底**——放置/资源决策可用表格、传输可用列表、拓扑可用设备/链路列表呈现；三维窗只是它们更直观的"另一种看法"。

## 3. 【核心⑥】三维动态拓扑展示窗（主舞台）

这是产品的门面。它在一个可旋转/缩放的三维场景里，**同时承载"集群拓扑 + 放置 + 传输 + 资源"四类信息**，并以流动方式呈现"正在发生什么"。

### 3.1 场景里有什么（静态结构）
- **设备节点**：每台在线设备一个三维实体。其上需可视化承载该设备的关键属性（功能性编码，不限定具体形态）：
  - 算力：总核 / 已承诺核 / 可用核；并行槽位 worker_slots（设备"强/弱"）。
  - 内存：已用 / 空闲 / 总。
  - 存储：总 / 空闲 / 已承诺配额。
  - 出口带宽：预算 / 已承诺。
  - 实时负载：CPU 使用率、当前运行任务数、放置预留数。
  - 网卡数（NIC）：多网卡设备需可识别（与多链路相关）。
  - 与中枢的 RTT、在线/离线状态。
- **链路边**：设备两两之间的网络边，承载**实测带宽与时延**（来自链路遥测，可能为空 → 给空态）。
- **任务覆盖层**：当前/选中任务的子任务，叠加显示在它们被放置到的设备上（子任务 → 设备的归属关系）。

### 3.2 场景里在动什么（动态过程，本窗的灵魂）
这些是**功能性动效**（用来传达"系统此刻在做什么"），必须能表达：
- **设备选择（放置）**：当某子任务被放置时，**候选设备集合**先被标识，被健康预筛淘汰的设备弱化，最终**选中的设备**被强调；若发生"就近放置（co-locate）以避免传输"，要能看出"本可跨设备、但被放到了一起"。
- **数据传输流**：当一条产物从上游设备传往下游设备时，在对应链路边上呈现**从源到目的的方向性流动**；流动的"粗细/速率"应能表达该传输的带宽档位（限速值）。传输完成即停止。
- **多链路分流（关键卖点，详见 §8）**：当一次传输走多条物理路径时，**同一逻辑传输被拆成多条并行的流**——分别沿"直连""经中继中转""不同网卡"的路径流动，并在下游"汇聚"；要能直观看出"多条路一起传比一条快"。
- **本地直读**：上下游同机时，**不产生跨设备流**，而是在该设备上给出"本地命中、跳过传输"的标识。
- **资源占用变化**：放置/分配发生时，目标设备的"已承诺核/内存/带宽/存储"实时增长；任务完成时回落（与 §7 账本联动）。
- **产物清理**：任务整图完成后，相关设备上的产物被回收（可选地给出轻量提示）。

### 3.3 交互能力
- **视角控制**：三维旋转、缩放、平移；一键复位；自动适配设备数量的布局。
- **点选**：
  - 点设备 → 弹出该设备详情（资源全维 + 正在跑的子任务 + 它的链路）。
  - 点链路边 → 该链路的实测带宽/时延 + 当前正在其上传输的产物。
  - 点子任务 → 跳到它的**放置决策**(③)与**资源决策**(④)与**传输构成**(⑤)。
- **图层开关**：可独立开/关——设备资源层、链路层、放置层、传输流层、多链路分流层、账本数值层。让演示者按需聚焦。
- **筛选/聚焦**：只看某个任务、某台设备、某类传输（如"只看走了中继的传输"）。
- **时间轴（与 §13 回放联动）**：可暂停、逐步、倍速回放一次任务的"放置→传输→完成"全过程；可拖动到任意时刻看当时的拓扑与账本快照。

### 3.4 四种工作模式（同一个三维窗，切换语义）
- **Live（实时）**：跟随真实集群与正在运行的任务，实时刷新。
- **Replay（回放）**：选一次历史运行，在时间轴上重演其全过程（用于讲解、复盘）。
- **Edit（拓扑编辑）**：进入 §4，在三维窗里直接增删设备/连边/设属性/拖拽布局。
- **Compare（对比）**：并排/叠加两次运行（如 plan vs random），直观对比放置与传输的差异（用于证明适配优化的价值）。

## 4. 【核心①】动态设备拓扑编辑

让用户**在三维窗（或配套面板）里直接编辑拓扑**，既能反映真实集群，也能搭建"假想拓扑"做规划与演示。

### 4.1 编辑能力
- **增 / 删 / 重命名设备节点**；自由拖拽布局，或一键自动布局。
- **设置设备属性**（功能性、与放置/资源决策相关）：
  - 并行槽位 worker_slots（"强/弱"设备）、总核数、内存容量、磁盘容量、网卡数(NIC)。
  - 角色标签（如"强算力""采集端"——仅作展示分组）。
- **连边定义链路**：在两台设备间建/删链路，**为链路设定带宽与时延**（用于规划与多链路演示）。
- **保存 / 载入拓扑**：多套拓扑情景可命名保存、随时切换。

### 4.2 两种数据来源（必须区分清楚）
- **Live 拓扑（只读映射）**：真实在线设备及其实测链路，从监控视图实时读出并自动成形。用户可调整布局，但设备的存在与真实资源不可编造。
- **Scenario 拓扑（what-if，可编辑）**：用户**虚构**的设备与链路，用于"如果有这样一组设备，放置/资源会怎么决策"的规划与演示。Scenario 拓扑可驱动**放置预览**（见 §5.4）。

> 说明（给前端工程师）：当前版本设备是真实进程注册上来的，前端**不能凭空启动设备**；"动态编辑拓扑"= 编辑**逻辑/规划拓扑 + 布局 + 链路标注 + 手动放置**，并实时映射真实集群。真正"跨网拉起设备"是下一版（Tailscale）的事，本前端为其预留拓扑编辑骨架。

### 4.3 手动放置（钉选）
- 把某子任务**拖到某设备**上 = 强制放置（directAllocationId）；或在节点编辑器里指定设备序号。
- 钉选的子任务在三维窗中显式标注"manual pin"，且**不参与自动放置与健康预筛**。
- 取消钉选 = 交还给适配优化自动决策。

## 5. 【核心②】智能放置过程可视化

不只展示"放在哪了"（结果），更要展示**"为什么这么放"（过程）**——这是科研卖点。

### 5.1 逐子任务的决策链（核心展示）
对每个被放置的子任务，按顺序呈现：
1. **候选设备集合**：本轮参与竞争的设备。
2. **健康预筛**：被淘汰的设备（CPU/内存/队列过载）被标记为"filtered out"并给出原因；若"全部过载 → 退回全量"也要可见。
3. **代价打分**：对每个候选给出代价分解——
   - 传输代价项（要从其它设备拉前驱产物的预计耗时，按实测链路带宽 × 数据量）。
   - 负载代价项（该设备已预留任务数 / 并行槽位）。
   - 综合代价（含权重 W_XFER / W_LOAD）。
4. **选中**：综合代价最低者被选中；若因"就近(locality)"把它放到已持有其输入数据的设备上 → 显式提示"避免了一次跨设备传输"。

### 5.2 三种放置模式的差异可视化
- **plan（整图前瞻）**：提交后对整张 DAG 反向就近规划一次；展示"整体布局"而非逐点贪心。
- **smart（逐节点贪心）**：每个就绪子任务即时按当前账本贪心选设备。
- **random（对照）**：随机放置，作为"无适配优化"的基线。
- 切换模式重跑，应能在 **Compare 模式**下并排看出放置布局与跨设备传输数量的差异。

### 5.3 在三维窗中的呈现
- 候选设备群体被标识 → 被筛掉的弱化 → 选中的强调；放置瞬间子任务"落"到设备上。
- 决策面板（点选子任务展开）：一张**候选设备 × 代价分项**的表 + 一句话结论"为何选它"。

### 5.4 放置预览（what-if，配合 §4.2 Scenario）
- 在不真正执行的情况下，对当前 DAG + 当前（真实或虚构）拓扑，**预演放置结果**：每个子任务会落到哪、会产生哪些跨设备传输、预计 makespan 量级。
- 用于"换一组设备/换权重/换模式，先看放置会怎么变"。

> **后端依赖（重要）**：放置的候选集、各候选代价分项、被筛设备、最终选择，**中枢在决策时已经算出**（目前以日志形式存在）。要支撑本节，需要后端把这些**以结构化"放置决策事件"输出**（每个子任务一条），见 §14.2。

## 6. 【核心③】适配优化 / 资源分配决策过程

放置决定"放哪台"，资源档位决定"给多少"。本节展示**四维资源档位是怎么被决定的**，以及**大脑账本如何随之增减**。

### 6.1 逐子任务的档位决策链
对每个子任务，展示四维（CPU 核 / 内存 / 带宽 / 存储）各自的定档来源：
- **是否显式声明**（用户在节点上填了 cores / mem_mb / bw_mbps / storage_mb）。
- **是否自动定档**：
  - 内存：按"算法历史边际内存 × 系数、设地板值"自动定（开关控制）。
  - 带宽：按"前驱实测产出大小 / 目标传输时延"自动估算需求（免手填）。
  - 存储：按"算法历史产出大小 × 系数、设地板值"自动定（开关控制）。
- **按设备可用收口**：最终档位被"该设备当前可用（总 − 已承诺）× 安全系数"夹住，展示"想要多少 vs 实际给多少 vs 设备还剩多少"。
- **算法历史画像驱动**：展示该算法的实测画像（峰值/边际内存、耗时、产出存储、样本数）如何喂给自动定档。

### 6.2 大脑账本的实时变化（防超卖的可视化）
- **分配即扣减**：子任务放置/派发时，目标设备的"已承诺核 / 内存 / 带宽 / 存储 / 放置预留"立即增长。
- **完成即归还**：子任务完成时回落；**超时未完成**（疑似设备崩溃）由系统自动回收预留，这一回收事件也应可见。
- 以"已承诺 / 可用 / 总"的动态条同时呈现四维 + 放置预留 + 在飞任务数。

### 6.3 与三维窗联动
- 选中子任务 → 在其所在设备上高亮其占用的四维档位；
- 设备节点上的"已承诺"随分配/归还实时涨落，让"资源被一份份分出去又收回来"可见。

> **后端依赖**：每个子任务的四维档位、定档来源（声明/自动/历史/收口）、账本前后值，中枢在 `_alloc_compute` 时已算出。需作为"资源决策事件"结构化输出，见 §14.2。

## 7. 【核心④】多维资源控制

展示平台能**对四类资源各自施加控制**，而不只是"看"。

### 7.1 四个维度（逐一可视 + 可配）
| 维度 | 控制手段 | 前端要展示/可配 |
|---|---|---|
| **CPU 算力** | 每任务绑核（限定可用核数） | 每子任务分到的核数、设备的核 已承诺/可用/总；可在节点上声明 cores。 |
| **内存** | 每任务内存硬上限 | 每子任务内存预算、设备内存 已承诺/空闲；可声明 mem_mb；自动定档开关。 |
| **出口带宽** | 每传输令牌桶限速 + 设备出口在并发流间**公平分享** | 每传输的限速值、设备出口 已承诺/预算；可声明 bw_mbps；自动带宽目标时延。 |
| **存储** | 每任务存储配额 + 产物生命周期回收 | 每子任务存储档位、设备磁盘 已承诺/空闲；可声明 storage_mb；自动定档开关。 |

### 7.2 产物生命周期治理（存储维度的一部分）
- 展示产物在设备上的占用；任务整图完成后产物被自动清理（回收）。
- 后台兜底回收（超龄 TTL / 磁盘水位上限按最旧优先清理）的策略值应可见/可配（只读展示其阈值即可）。

### 7.3 与决策的关系
- 资源控制是"施加"，§6 是"决策怎么定档"；前端应让二者衔接：决策定了多少 → 设备侧就按多少施加 → 账本体现已承诺。

## 8. 【核心⑤】多链路传输可视化

这是数据面的核心卖点：**一次传输可以同时走多条物理路径并行，带宽叠加**。前端要把"一条逻辑传输 = 多条物理路径"讲清楚。

### 8.1 五种传输形态（必须能区分展示）
1. **本地直读**：上下游同机 → 不走网络，标识"local hit, skip transfer"。
2. **单链路直连**：一条 QUIC 连接，源 → 目的。
3. **中继多链路**：直连带宽不足时，选一个**中继设备**新建第二条路径（数据经中继中转回源拉取），与直连**并行分条带传输**后在下游聚合。
4. **多网卡聚合**：源设备有多块网卡时，对其多个地址并行建多条连接，分流到不同网卡，带宽叠加。
5. **叠加（多网卡 + 中继）**：上述两者同时生效，多条路径一起传。

### 8.2 每次传输要展示的信息（点选一条传输 / 一条边）
- 该传输的**逻辑信息**：产物大小、源设备、目的设备、限速档位。
- 该传输的**物理路径构成**：用了几条路、每条路是"直连 / 经哪台中继 / 走哪块网卡"。
- 是否触发多链路、触发原因（带宽不足 / 多网卡可用）、是否聚合成功、近似聚合带宽。

### 8.3 在三维窗中的呈现
- 一次多链路传输 → **同一对源-目的之间出现多条并行的流**：
  - 中继路径要**途经中继设备节点**（体现"绕路中转"）；
  - 多网卡路径要体现"从源的不同网卡出去"；
  - 多条流在下游**汇聚**为一个完成事件。
- 直观对比：单链路一条流 vs 多链路多条流并行 → "多条更快"一目了然。
- 配合 §13 回放，可逐帧看"分条带 → 各路并行 → 汇聚重组"。

### 8.4 触发与开关
- 展示多链路相关开关与阈值（是否启用中继多链路 / 多网卡、最小触发产物大小、增益阈值）；
- 这些可作为"可调参数"展示（与 §9 系统参数一致）；演示时可开/关对比。

> **后端依赖**：每次传输的源列表（含每条路是直连/中继/网卡、是否带回源地址）、产物大小、限速，中枢在构造传输计划时已算出（日志有 `多链路源=N`）。需作为"传输计划事件"结构化输出，见 §14.2。

## 9. 任务编排（DAG 编辑器）

操作入口：把任务画成 DAG 并提交。

- **模板区**：一排可一键载入的预置 DAG（载入后可再编辑），覆盖典型场景：
  - 最小链路；跨设备数据（产出 → 消费）；扇入融合（多产出 → 一融合）；协同感知（图左右半 → 两设备各提特征 → 融合分类）；归约树（多级归约）；并行算力（多核矩阵乘）；**多链路演示（大产物 + 多设备，便于触发中继/多网卡）**。
- **节点编辑器**：每个节点可设
  - 算法（下拉，见 §12 算法目录；切换算法带出对应参数表单）；
  - 前驱依赖（多选其它节点 id，决定执行顺序与数据流）；
  - 算法参数（随算法而变）；
  - **四维资源档位**（可留空 = 自动）：cores / mem_mb / bw_mbps / storage_mb；
  - **固定设备**（钉选；-1 = 交给适配优化）；
  - 增 / 删节点、编辑任务名。
- **DAG 预览**：按拓扑分层画节点 + 依赖边，随编辑实时更新。
- **提交**：一键提交 → 进入运行结果页并开始查询；提交即进入三维窗 Live 模式跟踪。
- **校验防呆**：依赖不成环；只暴露安全参数（端口等易错项不开放）。

## 10. 任务列表 · 运行结果 · 对比

既是**基础功能**（任务的列表/详情/历史/重跑——见 §2.5"任务生命周期"），也是**价值证明**（用结果对比展示适配优化收益）。

- **任务列表与状态**：可浏览已提交的任务及其状态（排队 / 运行中 / 完成 / 失败 / 超时），可按时间/名称/状态排序筛选；点开任一任务进入其详情/结果；支持基于历史任务**重跑 / 改参重提**（这正是 plan vs random、多链路开/关 等对比的入口）。
- **指标卡**：makespan、节点数、**跨设备传输数 / 总边数**、用到设备数、错误数、**多链路传输数**。
- **放置与执行图**：DAG 图，节点按所在设备分组，跨设备传输的边显式标注，出错节点高亮；一眼看出"哪些被放一起省了传输、哪些被铺开抢并行"。
- **节点明细表**：每节点的设备、耗时、产出大小、结果（出错标红）。
- **历史运行**：最近若干次，可回看并进入 §13 回放。
- **对比（Compare）**：两次运行并排（如 plan vs random / 多链路开 vs 关），对比 makespan、跨设备传输数、放置布局、传输路径数——**这是演示卖点的关键页**。

## 11. 集群监控概览

打开即见集群态势（实时刷新，~2 秒）。

- **汇总指标卡**：在线设备数、可用核/总核、在飞任务数、当前运行任务数、已承诺出口带宽合计、已承诺存储合计。
- **每台设备一张卡**：CPU 使用率、内存(已用/总)、**核 已承诺/可用/总**、worker_slots、当前运行任务数、**放置预留**、**已承诺带宽/存储**、磁盘(空闲/总)、网卡数、RTT；强/弱设备标识。
- **设备间链路**：实测带宽/时延（可能为空，给空态）。
- **算法历史画像**：每算法的峰值/边际内存、耗时、产出存储、样本数。
- **状态**：加载中 / 无设备（提示去启动设备）/ 断连重连。

## 12. 系统参数 与 算法库

### 12.1 系统参数
- **安全可调（在线生效）**：放置模式（plan/smart/random，附简释）、放置权重 W_XFER / W_LOAD、自动内存定档开关、自动带宽目标时延、自动存储定档开关、健康预筛开关、多链路开关与阈值（启用与否、最小产物、增益）。保存后回显当前生效值。

## 13. 演示 / 回放模式（贯穿能力）

支撑②③⑤的"过程"展示，也是对外演示的利器。

- **录制**：每次运行自动记录一条"过程轨迹"——按时间排列的事件序列（放置决策、资源决策、各传输的开始/路径/结束、账本涨落、完成、清理）。
- **回放**：在三维窗里按时间轴重演任意历史运行；支持暂停、逐步、倍速、跳转任意时刻；任意时刻可查看当时的拓扑 + 账本快照。
- **讲解锚点**：可在轨迹上标记关键时刻（如"此处触发了中继多链路""此处就近放置省了传输"）便于演示。

## 14. 后端数据契约（保证每个功能可落地）

### 14.1 已有数据源（现在就能用）
- **集群监控视图**（中枢每 ~5 秒发布到 Redis，含设备四维资源 + 链路遥测 + 网卡列表 + 大脑账本 + 算法画像 + 在飞任务）。→ 支撑 §3 静态结构、§7 账本、§11 监控。
- **DAG 提交 / 结果**（提交 dagData；完成回 dagResult，含 makespan + 每节点的 deviceId/耗时/结果）。→ 支撑 §9 提交、§10 结果、放置**结果**着色、跨设备传输统计。
- **算法 / 设备 / 策略清单**查询、**算法上传**。→ 支撑 §12。

### 14.2 需要后端新增的"过程事件流"（②③⑤的过程展示依赖它）
要把"放置/资源/传输的**决策过程**"讲清楚，需要中枢把它**当下已经计算出来**的中间结果，作为**结构化事件**实时推给前端（建议 WebSocket 或事件订阅）。每类事件按子任务/传输粒度，至少包含：
- **放置决策事件**：task/子任务、候选设备列表、被健康预筛淘汰的设备及原因、每个候选的代价分项（传输项/负载项/综合）、最终选中设备、是否就近命中。
- **资源决策事件**：task/子任务、四维（核/内存/带宽/存储）各自的"需求 → 来源(声明/自动/历史) → 按设备可用收口 → 最终值"、分配后账本各维的前后值。
- **传输计划事件**：task/传输、产物大小、源、目的、限速、物理路径列表（每条：直连/中继(经哪台)/哪块网卡）、是否多链路及触发原因、是否本地直读。
- **生命周期事件**：子任务开始/完成、产物注册/清理、预留超时回收。

> 这些值中枢现在都已算出（多以日志形式存在：放置代价、`[alloc]` 资源、`[multipath] 多链路源=N`、`[cleanup]`/`[reclaim]`）。**本前端的②③⑤过程可视化与⑥三维流动，强依赖把它们提升为结构化事件输出**——请前端工程师与后端就这套事件 schema 达成约定，作为本前端的对接前提。

### 14.3 桥接层
- 浏览器 ↔ 一个 Web 桥接服务 ↔ 中枢（TCP）/ Redis。监控直接读 Redis；提交/结果/事件流经桥接。
- 建议把桥接做成干净的 **JSON + WebSocket** 接口（监控、提交、结果、**事件流**、配置、算法），并把"与后端对接"收敛到前端一处接口层，便于后续协议演进。

## 15. 非功能需求

- **实时性**：监控 ~2 秒刷新、三维窗事件流低延迟；增量更新、不闪烁、不卡顿；设备/事件较多时仍流畅。
- **健壮性**：完善的 加载 / 空 / 错误 / 断连重连 状态；无设备或超时要友好提示，绝不白屏或一直转圈。
- **响应式**：适配常见桌面分辨率与投屏演示。
- **离线**：不依赖运行时外网（库/资源本地化）；部署机可能无外网。
- **界面语言**：全部英文；数字/时间/单位格式统一规范。
- **可维护**：组件化；与桥接/事件流的对接收敛到清晰的接口层。
